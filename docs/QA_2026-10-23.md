## Paiements : périmètre exact

Le système reste strictement Sandbox. Sur Netlify : `FEDAPAY_ENABLED=false`, `FEDAPAY_ENVIRONMENT=sandbox`. Le code refuse Live et les clés Live. Aucun paiement réel déclenché.

Les tables et les deux RPC Sandbox existent sur le projet distant. Un test exécuté sur PostgreSQL distant, dans une transaction annulée par ROLLBACK, a contrôlé :

1. Création d'une tentative et calcul du montant depuis une variante existante.
2. Réutilisation de la même référence avec la même clé d'idempotence.
3. Passage à `paid`, puis réception d'un état `pending` tardif : état final toujours `paid`.
4. Stock commercial inchangé.

Ce test utilise un identifiant fournisseur fictif ; il n'appelle pas FedaPay et ne prouve pas une transaction fournisseur. Aucune donnée du test n'a été conservée, hormis l'avancement normal d'une séquence SQL.

**Blocage des transactions FedaPay de bout en bout :** Netlify ne contient que les deux variables publiques Supabase à la reprise ; aucune clé FedaPay Sandbox ni clé serveur Supabase. Impossible d'attester un checkout fournisseur, un paiement approuvé/refusé ou un webhook reçu depuis FedaPay sans ces accès. Aucun succès fournisseur n'est simulé dans le bilan.

Pour finaliser les essais, renseigner dans les variables sécurisées Netlify du contexte de prévisualisation : `FEDAPAY_SECRET_KEY` (`sk_sandbox_…`), `FEDAPAY_WEBHOOK_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `PAYMENT_RECONCILE_SECRET`, une URL HTTPS de retour, puis `FEDAPAY_ENABLED=true` pour ce contexte uniquement. Configurer le webhook Sandbox vers `/api/payments/webhook`, redéployer la prévisualisation et utiliser un compte staff autorisé. Tester succès, refus, annulation, expiration, double clic, webhook dupliqué/tardif et réconciliation. Ne pas ouvrir Live.

Références officielles : https://docs-v1.fedapay.com/payments/transactions et https://support.fedapay.com/portal/fr/kb/articles/comment-int%C3%A9grer-fedapay-%C3%A0-mon-application .

## Limites de validation

Les parcours authentifiés de l'administration ne sont pas attestés par un compte staff dans cette reprise. Les données sont vérifiées via Supabase et le contrôle d'accès public est testé sur le site après publication. L'avis Supabase conserve l'alerte de protection des mots de passe compromis désactivée et les fonctions SECURITY DEFINER existantes ; aucune modification d'authentification hors périmètre n'est effectuée.

Le bilan de conversation fournit le commit réellement publié, le déploiement Netlify et les résultats des contrôles publics après déploiement.
