# Terrain 18 — Code e-mail du back-office

Supabase Auth vérifie le mot de passe et reste responsable de la session et de sa révocation. Le code à six chiffres est envoyé par Resend à l’adresse confirmée de l’identité réservée. Il expire en cinq minutes. PostgreSQL autorise cinq essais par code, un envoi par minute et cinq envois par heure et par compte. Un renvoi remplace le code précédent. Le code ne change pas le niveau AAL émis par Supabase.

La preuve de validation réside dans le schéma privé, associée à l’identité et à l’identifiant de session Supabase. La validation et la consommation du code forment une opération atomique. La garde PostgreSQL existante s’applique à chaque accès administratif, y compris les requêtes directes. Le renouvellement des jetons conserve la preuve de la même session. Un nouveau mot de passe saisi lors d’une connexion crée une autre session. La limite de 30 jours s’applique à partir de la session Auth d’origine et de son authentification par mot de passe.

## Pilote de production

1. Garder une session du propriétaire ouverte dans le navigateur principal et vérifier séparément l’accès de récupération à Supabase, GitHub et Netlify. Identifier le dernier déploiement publié et le point de récupération de la base.
2. Après accord du propriétaire, renseigner la variable privée `ADMIN_EMAIL_OTP_SECRET` dans le contexte production des fonctions Netlify. Générer 32 octets aléatoires avec un gestionnaire de secrets et les encoder en hexadécimal (64 caractères). Vérifier la présence de `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY` et `ORDER_EMAIL_FROM`. Conserver les valeurs existantes et leur confidentialité.
3. Après accord, appliquer uniquement `20261121203637_admin_email_otp.sql` et lancer `supabase/production/admin-email-otp-postflight.sql`. Vérifier tous les résultats puis déployer le commit approuvé. Garder les deux drapeaux d’obligation désactivés pendant le pilote. Seul le propriétaire technique peut encore utiliser une session hors pilote pendant cette transition.
4. Dans un navigateur séparé, ouvrir `/admin/login?otp=1`. Saisir son mot de passe, relever le code dans sa boîte, puis le saisir sur le site. Conserver le navigateur principal connecté. Confirmer le blocage d’une page admin avant le code et l’accès après validation. Vérifier la persistance en fermant complètement puis en rouvrant le navigateur de test. Depuis ce navigateur, utiliser « Me déconnecter » et vérifier que la session de test est refusée. Éviter la révocation globale durant le pilote.
5. Contrôler le journal privé pour la session testée. Les événements `issued`, `accepted` et `verified` confirment respectivement la création du défi, la prise en charge par Resend et la validation. L’accès à la boîte est confirmé par le titulaire. Le journal ne contient aucun code, jeton ou contenu de message.
6. Après validation réelle et nouvel accord, activer `private.security_flags.admin_email_otp_required` via le compte habilité Supabase. Vérifier le refus des anciennes sessions sans preuve et le succès d’une nouvelle connexion avec code. La responsable accepte elle-même son invitation et choisit son mot de passe. Une intervention habilitée rattache ensuite uniquement son identité confirmée avec `private.bind_authorized_admins()`. Elle doit réussir son propre parcours OTP avant d’accéder au studio.

## Retour arrière

Si le pilote échoue, garder l’obligation e-mail désactivée et conserver le navigateur principal du propriétaire. En cas d’incident nécessitant un retour à Terrain 17C, suivre la procédure de récupération avec l’accès habilité Supabase et Netlify. L’intervention approuvée consiste à appliquer `supabase/production/rollback-admin-email-otp.sql`, puis à republier le dernier déploiement sain. Le SQL rétablit la garde Terrain 17C et laisse les journaux en place. Révoquer ensuite les sessions concernées via Supabase Auth. En cas de perte de la boîte, rétablir l’accès à la boîte par sa procédure officielle de récupération. Toute modification du rattachement d’identité nécessite une décision distincte du propriétaire.
